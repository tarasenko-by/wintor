# Architecture

A map for contributors: where things live and how data flows. The rules are in [AGENTS.md](../AGENTS.md),
the look in [DESIGN.md](DESIGN.md).

## Three layers

```
Wintor.App  (WinUI 3: views, view models, services)
    │  uses only ITorrentEngine and the records from Core
    ▼
Wintor.Core  (plain .NET: ITorrentEngine, snapshots, formatting, parsing — no UI, no MonoTorrent)
    ▲
    │  implements ITorrentEngine
Wintor.Engine.MonoTorrent  (the only place that references MonoTorrent)
```

You can work on one layer without knowing the others. A new engine feature is: a method or a field in
`Core`, its implementation and test in `Engine.MonoTorrent`, then the UI in `App`.

| Where | What |
|---|---|
| `Core/ITorrentEngine.cs` | Everything the app can ask the engine: add, start, pause, remove, details, limits, priorities |
| `Core/TorrentSnapshot.cs` | Immutable state of one torrent at one moment — what the table shows |
| `Core/TorrentDetails.cs` | Files, peers, trackers and piece maps for the details pane |
| `Core/TorrentProblem.cs` | Failures the UI can explain (files missing, disk full, no access) |
| `Core/TorrentQuery.cs`, `Formatting.cs`, `TorrentInput.cs`, `RateMeter.cs` | Filtering/sorting, human-readable sizes and speeds, magnet/file detection, payload speed |
| `Engine.MonoTorrent/MonoTorrentEngine.cs` | The adapter: state files, start/pause bookkeeping, mapping MonoTorrent types to Core records |
| `App/ViewModels` | `TorrentsViewModel` (the table, filters, labels, queue), `TorrentDetailsViewModel`, `SettingsViewModel` |
| `App/Views` | Pages and dialogs; dialogs and pickers live in code-behind |
| `App/Services` | Settings, strings, dialogs, tray icon, notifications, theme/backdrop, shell helpers |
| `App/Controls` | Small custom controls: piece bar, speed graph, splitter, column resizer |
| `App/Icons` | Hugeicons rendered as `PathIcon`s; `HugeIcons.g.cs` is generated by `tools/Wintor.IconTool` |

## Data flow

The engine is not observed through events. `TorrentsViewModel` asks for `GetSnapshots()` once a second
(a `DispatcherQueueTimer`, so it runs on the UI thread) and updates its rows **in place**: one
`TorrentItemViewModel` per torrent, kept by id, so the list never flickers and selection survives.
The details pane does the same with `GetDetailsAsync` for the selected torrent only.

Commands go the other way: a view model calls the engine (`StartAsync`, `SetSpeedLimitsAsync`, …) and then
refreshes right away instead of waiting for the next tick.

## State on disk

All under the app's local data folder (`AppSettings` knows the path):

| File | Owner | Holds |
|---|---|---|
| `settings.json` | `AppSettings` | Preferences, labels and their colors, queue order, column layout |
| `engine.state` | MonoTorrent | The torrents themselves (restored on launch) |
| `cache/` | MonoTorrent | Fast-resume data, magnet metadata, DHT nodes |
| `paused.txt` | engine adapter | Ids the user paused — MonoTorrent restores everything as stopped |
| `had-data.txt` | engine adapter | Ids that had downloaded data, to notice when their files were deleted |

State is saved on every change and on a graceful exit (`wintor --quit`, tray → Exit). Killing the process
can lose the last few seconds of progress, which a recheck recovers.

## Process model

- **Single instance** (`Program.cs`): a second launch — a `.torrent` double-click, a `magnet:` link, the Start
  menu — is redirected to the running instance and routed in `App.Route`. Two instances would overwrite each
  other's state.
- Closing the window hides it; Wintor keeps seeding in the notification area (`TrayIcon`).
- Packaged as MSIX (`Package.appxmanifest`): file and protocol associations, the `wintor` execution alias,
  start with Windows.

## Tests

- `tests/Wintor.Core.Tests` — pure logic, fast.
- `tests/Wintor.Engine.MonoTorrent.Tests` — the real engine against temporary folders: a legal magnet link that
  stays in the metadata phase and small torrents made from generated files. No downloads.
- `tests/ui/ui-tests.ps1` — UI Automation in the background (or in Windows Sandbox). What it cannot judge goes
  to `tests/ui/manual-checks.md`.
